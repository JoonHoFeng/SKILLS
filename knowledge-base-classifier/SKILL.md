# 知识库文档分类判断 Skill

## 目标

当用户正在撰写、准备提交或评审知识库文档时，依据《研发中心创新攻坚与技术沉淀建设制度（V1.2）》进行分类判断。

需要完成以下任务：

1. 判断文档属于：
   - 创新攻坚
   - 优秀设计
   - 经验分享
2. 在证据充分时继续判断等级：
   - 创新攻坚：S / A / B / C
   - 优秀设计：S / A / B / C
   - 经验分享：A / B / C
3. 给出判断理由。
4. 指出当前文档缺失的关键信息。
5. 给出“如何修改后更符合目标分类/等级”的建议。
6. 对明显不满足申报要求、疑似低质量方案的内容进行提醒。

---

# 一、总分类原则

先判断文档“主要产出物是什么”，不要只看标题。

## 1. 创新攻坚

适用于：

- 输出创新型应用解决方案；
- 目标通常与降本增效、风险识别、关键技术难点突破有关；
- 重点不仅是“记录做法”，而是提出新的方案、改进路径或创新思路；
- 应体现：
  - 问题现状
  - 创新方案
  - 创新点
  - 实施路径
  - 落地效果
  - 推广价值

典型关键词：

- 创新方案
- 技术突破
- 重构
- 优化
- 降本增效
- 风险识别
- 新机制
- 新架构思路
- 自动化改造
- 性能突破
- 成本降低
- 试点
- 可行性验证
- 行业趋势

### 创新攻坚等级

#### S级：突破式战略创新

满足以下特征：

- 前瞻性、领先性强；
- 与现有技术路径差异显著；
- 可推动公司产品升级；
- 或可使公司技术能力实现跨代突破。

落地要求：

- 已落地：必须说明可验证的落地效果；
- 未落地：必须有完整可行性分析，并提供验证报告或小范围试点数据，且明确落地路径。

#### A级：迭代式应用创新

满足以下特征：

- 攻克现有技术难点；
- 基于现有技术做重构、整合或优化；
- 明显突破常规改进思路；
- 解决实际工作中的关键痛点；
- 效果超出一般优化。

#### B级：落地式实效创新

满足以下特征：

- 面向日常工作中的具体问题；
- 基于已有技术或流程进行调整、补充、改进；
- 创新突破不强；
- 但能有效解决实际问题、降低成本或提升效率。

#### C级：探索式提案创新

满足以下特征：

- 聚焦业务场景、潜在需求或具体问题；
- 提出了可行、有启发性的创新思路；
- 暂未形成完整方案或未落地；
- 具备进一步孵化价值；
- 符合部门技术发展需求和行业趋势；
- 不存在明显可行性漏洞。

要求：

- 必须具备完整可行性分析；
- 不强制要求落地或试点数据。

---

## 2. 优秀设计

适用于：

- 来源于日常项目资产；
- 核心是高质量业务设计或技术设计；
- 强调“设计质量”，而不是“创新程度”；
- 能够高效、低成本实现项目需求；
- 通常无需单独提出新课题，项目过程中自然沉淀即可。

先判断设计对象，再判断等级。

### S级：架构设计类

典型内容：

- 系统架构
- 技术架构
- 部署架构
- 高可用设计
- 容灾设计
- 分布式架构
- 数据架构
- 服务拆分
- 集群拓扑

价值要求：

- 高可用
- 高扩展
- 高稳定
- 兼顾当前需求与未来扩展
- 支撑性能优化
- 支撑成本降低

### A级：接口设计类

典型内容：

- 内部模块接口
- 外部系统接口
- API 设计
- 协议设计
- 数据交互设计
- 系统集成接口

价值要求：

- 易用性
- 兼容性
- 安全性
- 可维护性

### B级：需求设计类

典型内容：

- 核心业务流程设计
- 功能逻辑设计
- 场景适配设计
- 业务规则设计
- 状态流转设计

价值要求：

- 更贴合业务
- 提升效率
- 提升用户操作便捷性

### C级：产品体验设计类

典型内容：

- UI 设计
- 交互设计
- 操作流程设计
- 页面体验优化

价值要求：

- 改善视觉体验
- 提升操作流畅度
- 提升用户满意度

> 注意：优秀设计的 S/A/B/C 本质上首先是“设计类别”，不是单纯按好坏从高到低打分。
> 如果文档内容同时包含多种设计，优先按文档的核心产出物、主要篇幅和主要价值确定主分类，并可附带“次要分类”。

---

## 3. 经验分享

适用于：

- 重点是发现问题、还原场景、分析原因、总结经验；
- 不强制要求给出解决方案；
- 更关注分析过程和经验提炼；
- 文档价值来自可复用的思考方式、排障方法、踩坑经验或实践结论。

建议结构：

- 场景还原
- 分析过程
- 核心结论
- 经验提炼

典型关键词：

- 故障排查
- 根因分析
- 问题复盘
- 踩坑
- 排障过程
- 原因定位
- 经验总结
- 注意事项
- 最佳实践
- 常见问题
- 现象分析

### 经验分享等级

#### A级

- 聚焦业务痛点或重大技术难题；
- 实践指导性高；
- 对跨项目有较高参考价值；
- 高复用；
- 具备明显推广意义。

#### B级

- 面向特定业务领域或常见场景；
- 可为同类型项目或部门同事提供直接参考；
- 实操性较强。

#### C级

- 面向具体项目或相对小众场景；
- 有一定借鉴意义；
- 仍具一定优化潜力。

# 二、分类决策顺序

必须按以下顺序判断：

## 第一步：识别主要目标

询问或从文档中识别：

- 是“提出并落地一个新方案”？
- 是“沉淀一个高质量设计”？
- 还是“复盘问题与分析经验”？

## 第二步：判断主分类

### 判定为“创新攻坚”的强信号

满足任意多个：

- 明确提出了“创新点”；
- 有新方案或新机制；
- 解决的是关键痛点；
- 有降本、提效、性能突破等效果；
- 有实施路径、试点、落地效果；
- 文档核心是“为什么这个方案比原来更好”。

### 判定为“优秀设计”的强信号

满足任意多个：

- 文档核心是架构、接口、业务流程、UI/交互设计；
- 不是为了证明“创新”，而是为了沉淀一个高质量设计；
- 内容可直接作为设计资产复用；
- 来源于实际项目设计。

### 判定为“经验分享”的强信号

满足任意多个：

- 从一个问题、故障、异常、踩坑出发；
- 重点描述排查过程；
- 强调根因分析；
- 主要价值是“以后遇到类似问题怎么判断/怎么排查”；
- 即使没有形成新解决方案，文档仍有价值。

---

# 三、冲突场景处理

## 1. 既有问题排查，又有解决方案

判断标准：

- 如果重点是“怎么定位问题、为什么发生、以后怎么排查”：
  - 归为经验分享。
- 如果重点是“提出了新的解决方案并实施，效果显著”：
  - 归为创新攻坚。
- 如果重点是“最终形成了一套架构/接口/业务流程设计”：
  - 归为优秀设计。

## 2. 架构优化是否一定属于优秀设计

不是。

- 如果只是项目架构设计沉淀：
  - 优秀设计-S。
- 如果通过明显不同于现有路径的新架构解决关键问题，并强调创新性、效果和推广价值：
  - 可归为创新攻坚。
- 若无法判断，优先输出：
  - 主分类
  - 候选分类
  - 需要补充的判定信息

## 3. 性能优化

- 常规参数调整、配置优化：
  - 通常不是高等级创新。
- 系统性重构、算法优化、存储模型变化、并发模型变化：
  - 可能属于创新攻坚 A 或 B。
- 仅记录排查过程和经验：
  - 经验分享。
- 如果沉淀的是整体性能架构设计：
  - 优秀设计-S。

# 四、低质量方案检查

若文档出现以下情况，需要明确提醒：

1. 与已入库方案高度重复；
2. 内容空洞，没有具体细节；
3. 没有创新点、设计亮点或分析深度；
4. 只是把常规操作重新包装；
5. 存在明显逻辑缺陷；
6. 无核心产出物或支撑数据；
7. 明显无法落地；
8. 不符合公司或行业应用场景；
9. 技术难度过低，网上很容易直接查到；
10. 结构混乱、表达不清。

不要仅因为“内容篇幅长”就认为质量高。

# 五、判断时需要提取的信息

分析知识库文档时，优先提取：

- 背景/场景
- 当前问题
- 原方案/原流程
- 核心痛点
- 新方案
- 创新点
- 架构/接口/流程设计
- 实施路径
- 排查过程
- 根因
- 数据验证
- 落地结果
- 性能提升
- 成本变化
- 稳定性变化
- 复用范围
- 推广价值
- 是否已落地
- 是否有试点
- 是否有数据
- 是否能跨项目复用

# 六、输出格式

每次判断必须按以下格式输出：

## 分类结论

- **主分类**：创新攻坚 / 优秀设计 / 经验分享
- **建议等级**：S / A / B / C / 暂无法定级
- **置信度**：高 / 中 / 低

## 判断依据

列出 3～6 条与文档内容直接对应的理由。

## 与制度要求的匹配

### 已满足
- ...

### 缺失或不足
- ...

## 是否存在其他候选分类

如果没有，写“无明显候选分类”。

如果有，例如：

- 候选：经验分享-B
- 原因：当前文档大量篇幅放在故障排查过程，如果弱化方案创新、强化排障复盘，则更接近经验分享。

## 建议补充内容

必须给出具体建议，例如：

- 增加原方案与新方案对比；
- 补充性能数据；
- 补充成本变化；
- 增加架构图；
- 增加适用范围；
- 增加落地效果；
- 增加可复用性说明；
- 增加问题根因链路；
- 增加试点数据；
- 增加创新点总结。

## 一句话结论

示例：

> 当前更适合归类为“经验分享-B”，因为文档核心价值在于故障排查和根因分析；如果补充新方案、实施效果与可推广价值，可能更接近“创新攻坚-B/A”。

---

# 七、信息不足时的处理

不要强行分类或定级。

如果缺少以下关键证据，应明确说明“暂无法准确定级”：

- 是否落地；
- 是否有验证数据；
- 是否属于项目设计资产；
- 是否有明确创新点；
- 是否有跨项目复用价值；
- 是否只是常规操作。

优先提出最多 5 个关键问题，例如：

1. 这个方案是否已经在项目中落地？
2. 相比原方案，核心变化是什么？
3. 是否有量化效果数据？
4. 能否复用于其他项目？
5. 文档重点是“方案设计”还是“问题排查过程”？

---

# 八、禁止事项

- 不要仅根据文档标题分类。
- 不要把所有“技术文档”都归为优秀设计。
- 不要把所有“解决问题”的文档都归为创新攻坚。
- 不要因为有“架构”二字就自动判为优秀设计-S。
- 不要因为有“故障”二字就自动判为经验分享。
- 不要在没有落地/验证证据时，将创新攻坚直接判为 S。
- 不要将经验分享判为 S 级，制度中经验分享只有 A/B/C。
- 不要把 S/A/B/C 简化理解成单纯质量排序，尤其优秀设计的等级同时对应不同设计类型。

---

# 九、推荐交互方式

当用户只给出题目时：

1. 先给“初步分类倾向”；
2. 明确置信度低；
3. 提醒需要正文或概要才能准确判断。

当用户给出正文时：

1. 直接分析；
2. 不必先询问；
3. 能定级则定级；
4. 不能定级则说明缺失信息。

当用户说“帮我把它改成创新攻坚A”或类似目标时：

1. 先判断现状；
2. 再列出与目标等级之间的差距；
3. 给出需要补充或重构的具体内容；
4. 不虚构不存在的数据、结果或创新点。

# 十、快速判断表

| 文档核心 | 主分类 |
|---|---|
| 新方案、新机制、技术突破、降本增效、关键问题解决 | 创新攻坚 |
| 系统架构、接口、业务流程、UI/交互等项目设计资产 | 优秀设计 |
| 故障排查、根因分析、踩坑、复盘、经验提炼 | 经验分享 |

| 创新攻坚等级 | 核心特征 |
|---|---|
| S | 战略级、突破式、技术路径差异显著、产品或能力跨代提升 |
| A | 攻克技术难点，重构/整合/优化明显超出常规改进 |
| B | 基于现有技术/流程的实效改进，可解决实际问题 |
| C | 有可行性和启发性的创新提案，尚未完全落地 |

| 优秀设计等级 | 主要内容 |
|---|---|
| S | 架构设计 |
| A | 接口/API设计 |
| B | 需求/业务流程/功能逻辑设计 |
| C | UI/交互/产品体验设计 |

| 经验分享等级 | 核心特征 |
|---|---|
| A | 重大难题、高指导性、跨项目、高复用 |
| B | 常见场景、同类型项目可直接参考、实操性强 |
| C | 具体项目或小众场景，有一定借鉴意义 |

# 十一、生成知识库文档时的文件结构规范

当用户要求“生成知识库文档”“整理成知识库方案”“输出知识库材料”时，除分类判断外，还必须按照以下目录结构生成文件。

## 1. 根目录命名

以**方案名**作为文件夹名称。

示例：

```text
ThingsBoard_Cassandra历史遥测数据修复方案/
```

目录名应：

- 优先使用用户给出的正式方案名；
- 不自行加入日期、版本号、作者名，除非用户明确要求；
- 去除操作系统不允许的特殊字符；
- 不随意缩写方案名。

## 2. 文件夹内只允许以下内容

```text
<方案名>/
├── <方案名>.md
├── 申报说明.txt
└── img/                  # 仅在文档实际有图片时创建
    ├── xxx.png
    └── xxx-2.png
```

### 强制规则

- 正文只生成 **1 个 Markdown 文档**；
- Markdown 文件名必须与方案名一致；
- 不生成 docx、pdf、html 等其他正文格式；
- 必须额外生成 `申报说明.txt`；
- 只有实际存在图片时才创建 `img/`；
- 没有图片时不要创建空 `img/` 文件夹；
- 图片统一放在当前方案目录下的 `img/` 中；
- 不得把图片散落到方案根目录；
- 不得使用绝对路径引用图片。

---

# 十二、Markdown 图片引用规范

所有图片必须使用相对路径。

正确示例：

```markdown
![系统架构图](./img/system-architecture.png)
```

```markdown
![故障链路](./img/error-chain.png)
```

错误示例：

```markdown
![系统架构图](/Users/xxx/Desktop/system.png)
```

```markdown
![系统架构图](C:\Users\xxx\system.png)
```

```markdown
![系统架构图](https://example.com/system.png)
```

除非用户明确要求引用外部图片，否则生成的知识库方案应优先将图片复制/生成到 `img/` 目录，再使用相对路径引用。

## 图片文件命名

优先采用能表达含义的英文或拼音文件名，例如：

```text
img/
├── system-architecture.png
├── deploy-topology.png
├── problem-flow.png
├── before-after.png
└── performance-result.png
```

避免：

```text
1.png
2.png
截图1.png
新建图片.png
```

如果图片由用户提供且无法改名，可以保留原文件名，但 Markdown 中仍必须使用相对路径。

# 十三、`申报说明.txt` 生成规范

`申报说明.txt` 用于单独生成该知识库方案的**申报说明概括**。

它不是知识库正文，不要把正文完整复制进去。

其内容必须根据最终判断出的知识库分类，参考制度中的“申报思路”进行概括。

## 1. 创新攻坚

制度中的申报思路为：

```text
问题现状 + 创新方案（说明创新点） + 实施路径 + 落地效果 + 推广价值
```

因此 `申报说明.txt` 应按以下结构生成：

```text
【方案名称】
<方案名>

【分类】
创新攻坚-<等级>

【申报说明】
问题现状：
<用 1~3 句话说明现状、痛点、影响>

创新方案及创新点：
<说明方案核心做法，以及与原有做法相比的新意>

实施路径：
<说明如何实施、验证、上线或推广>

落地效果：
<优先写量化结果；没有数据时必须明确写“暂无量化数据”，不得虚构>

推广价值：
<说明适用范围、可复制性、跨项目价值>
```

### 生成要求

- 必须把“创新点”写清楚；
- 如果方案只是常规优化，不要人为包装成重大创新；
- 有性能、成本、效率、稳定性等数据时优先使用量化结果；
- 尚未落地时必须如实说明当前处于：
  - 可行性分析
  - 验证
  - 试点
  - 待推广
  中的哪一阶段；
- 不得虚构落地数据或推广范围。

---

## 2. 经验分享

制度中的申报思路为：

```text
场景还原 + 分析过程 + 核心结论 + 经验提炼
```

因此 `申报说明.txt` 应按以下结构生成：

```text
【方案名称】
<方案名>

【分类】
经验分享-<等级>

【申报说明】
场景还原：
<说明问题发生的业务/技术背景、现象、影响>

分析过程：
<概括关键排查步骤、判断依据、排除过程>

核心结论：
<说明最终根因、关键发现或结论>

经验提炼：
<说明以后遇到类似问题时，可复用的判断方法、排查路径、注意事项>
```

### 生成要求

- 不要把整个排查日志复制进申报说明；
- 重点保留“为什么这么判断”的核心链路；
- 如果有多个根因，按主次概括；
- 经验提炼必须尽量形成可复用的方法，而不是只写“问题已解决”。

---

## 3. 优秀设计

制度对“优秀设计”明确说明：

- 项目来源于日常工作中的项目资产；
- 无需再单独提报。

制度没有像“创新攻坚”和“经验分享”一样给出独立的“申报思路”公式。

因此，当最终分类是“优秀设计”时，仍按用户要求生成 `申报说明.txt`，但必须将其视为**辅助申报摘要**，不得声称下面的结构是制度原文规定。

建议结构：

```text
【方案名称】
<方案名>

【分类】
优秀设计-<等级>

【申报说明】
项目背景：
<说明该设计来自哪个项目/业务场景，以及解决什么需求>

设计对象：
<架构 / 接口 / 需求流程 / UI交互 等>

核心设计：
<概括最关键的设计思路和技术要点>

设计价值：
<说明对高可用、扩展性、稳定性、兼容性、安全性、效率、体验等方面的价值>

复用范围：
<说明是否可用于其他项目、模块或类似场景>
```

### 等级对应提醒

- S：架构设计类
- A：接口设计类
- B：需求设计类
- C：产品体验设计类

优秀设计的等级首先要依据设计类型判断，不能为了提高等级而把接口设计强行写成 S 级。

# 十四、申报说明长度与写法

`申报说明.txt` 应做到：

- 信息密度高；
- 可直接复制到申报系统或用于评审简介；
- 默认控制在 **300~800 字**；
- 简单方案可以更短；
- 复杂方案可适当超过 800 字，但仍应明显短于 Markdown 正文；
- 使用事实描述；
- 不写空泛口号；
- 不虚构数据；
- 不重复大段源码、日志、SQL 或配置文件。

如果正文中的证据不足，应在 `申报说明.txt` 中明确使用：

```text
待补充：<缺失内容>
```

例如：

```text
落地效果：
当前已完成测试环境验证。
待补充：生产环境性能提升数据、资源消耗对比。
```

不要为了让申报说明“看起来完整”而生成不存在的事实。

# 十五、完整生成流程

当用户要求生成一篇知识库文档时，按照以下流程执行：

1. 获取或识别方案名称；
2. 分析用户提供的材料；
3. 判断主分类；
4. 判断建议等级；
5. 按对应分类组织 Markdown 正文；
6. 判断是否需要图片；
7. 如有图片：
   - 创建 `img/`；
   - 将图片放入其中；
   - 全部使用 `./img/...` 相对路径；
8. 创建 `<方案名>.md`；
9. 创建 `申报说明.txt`；
10. 检查是否存在低质量方案风险；
11. 检查目录中是否存在不应该生成的其他文件；
12. 最终向用户说明：
   - 分类
   - 等级
   - 生成目录
   - 正文文件
   - 申报说明文件
   - 图片数量（如有）

# 十六、按分类组织 Markdown 正文

Markdown 的实际章节可以根据内容调整，但默认优先采用以下结构。

## 创新攻坚正文模板

```markdown
# <方案名称>

## 1. 背景与问题现状

## 2. 现有方案及痛点

## 3. 创新方案

### 3.1 整体思路

### 3.2 核心创新点

### 3.3 技术方案 / 架构设计

## 4. 实施路径

## 5. 验证与落地效果

## 6. 推广与复用价值

## 7. 总结
```

## 优秀设计正文模板

```markdown
# <方案名称>

## 1. 项目背景

## 2. 设计目标

## 3. 需求与约束

## 4. 方案设计

### 4.1 整体设计

### 4.2 核心设计点

### 4.3 关键流程 / 接口 / 架构

## 5. 设计价值

## 6. 可复用性与适用范围

## 7. 总结
```

## 经验分享正文模板

```markdown
# <方案名称>

## 1. 场景与问题现象

## 2. 问题影响

## 3. 分析与排查过程

### 3.1 初步判断

### 3.2 排查步骤

### 3.3 关键证据

## 4. 根因分析

## 5. 处理方式

## 6. 核心结论

## 7. 经验提炼

## 8. 总结
```

模板不是为了强制凑章节。

如果某一章节没有真实内容，可以：

- 合并章节；
- 删除章节；
- 标记待补充。

禁止虚构内容填满模板。

# 十七、生成结果检查清单

生成前必须检查：

```text
[ ] 文件夹名称是否与方案名一致
[ ] 是否只有一个 Markdown 正文
[ ] Markdown 文件是否与方案名同名
[ ] 是否生成了 申报说明.txt
[ ] 没有图片时是否未创建 img/
[ ] 有图片时是否全部放入 img/
[ ] Markdown 中图片是否全部使用相对路径
[ ] 是否已经完成分类判断
[ ] 是否已经完成等级判断或明确说明无法定级
[ ] 申报说明是否符合对应分类的申报思路
[ ] 是否存在虚构的落地效果、性能数据或推广范围
[ ] 是否存在低质量方案风险
```
